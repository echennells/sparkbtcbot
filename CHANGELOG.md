# Changelog

## Unreleased

### Added

- **Sealed policy engine** (`lib/policy.js`). The seed-bound policy grows from `{ dailyBudgetSats }` to `{ dailyBudgetSats, maxPerTxSats, allowedOps, allowedRecipients, expiresAt, exec }` — every key optional, unknown keys refused at boot. Every `SparkAgent` money-moving method now runs one gate (`#authorize`) before any network call: the file allowlist, then the sealed rules in order `expiresAt → allowedOps → allowedRecipients → maxPerTxSats`, then the operator's **executable hook** — a program pinned by sha256 in the sealed policy (the agent's process cannot repoint or swap it), fed the request context on stdin, answering `{"allow", "reason"}` on stdout; every failure class (non-zero exit, bad JSON, no boolean, > 5 s, missing, modified, not executable) is a deny. The context carries the real amount and the wallet's real rolling daily total. Dry runs evaluate the built-in rules but never fire the hook. A denial throws `PolicyDeniedError { code: "POLICY_DENIED", rule, reason }`; `agent.policy()` returns the active limits read-only. `set-policy` gains `--file policy.json` (seals the whole object, pins the hook's hash from the file on disk) and `--show`; the no-flag flow edits the budget and preserves the other rules. Fee ceilings and the signed ledger are unchanged — policy sees the request, fee guards see the quote. The wire contract for the hook is the one MoonPay's Open Wallet Standard documents for executable policies (MIT); the enforcement and the sealing are ours. `references/security.md` → Policy engine has the rule table and the fail-closed table as a written contract.
- **Audit log** (`lib/audit-log.js`): one JSON line per policy denial and per live money-moving outcome at `~/.spark/audit.jsonl` (`SPARK_AUDIT_LOG_PATH`, `SPARK_AUDIT_LOG=off`). Never a passphrase, mnemonic, preimage, or raw invoice; `append()` refuses secret-shaped keys as a backstop. A log write failure warns once and never blocks a spend.
- **`sparkbtcbot rekey [--generate]`** — change the seed.enc passphrase: decrypt under the current one (typed, never `.env`), re-encrypt the same mnemonic and sealed policy under the new one with a fresh salt and IV, atomic swap; `--generate` mints a random 24-character passphrase shown once. TTY-gated like `set-policy`. The ledger and leaf-vault are keyed by the mnemonic and are untouched. Prints the update checklist and the caveat that copies of the old file still open with the old passphrase — for a copied file the answer is a new wallet, not a new passphrase (`references/security.md` → Rekey vs. rotate).
- **`sparkbtcbot rotate [--execute]`** — the revocation primitive SKILL.md always prescribed ("sweep to a new wallet") as a command. Dry run by default. With `--execute`: boots the current wallet and a fresh one, refuses while an unclaimed L1 deposit waits, writes the new seed to `seed.enc.next` and the old to `~/.spark/retired/<date>-<pubkey>/seed.enc` **before** any sweep (an interrupted run leaves both seeds complete on disk and prints how to finish by hand), enables privacy on the new wallet before it receives anything, sweeps sats and every token and waits for the new wallet to claim them, then renames the new seed into place, files the old leaf-vault beside the retired seed, resets the signed ledger if a budget is sealed (the sealed policy carries over), snapshots a fresh vault, and prints what went stale (the old static L1 deposit address is valid forever; old invoices still pay). The retired seed is an ordinary `seed.enc` under the same passphrase — every command works on it via `SPARK_SEED_PATH`; no purge, no new subcommands. Exercised end to end on REGTEST.
- **`SPARK_PASSPHRASE_FILE`** — read the passphrase from a file (trailing newline stripped) for systemd `LoadCredential` / Docker secrets; `SPARK_PASSPHRASE` wins if both are set.

## 0.8.0 — 2026-09-15

### Security

- **Wallet privacy is now enabled by default.** Spark wallets are publicly readable out of the box — the operators' per-identity `private_enabled` setting defaults to false, and while it is false anyone holding the Spark address can read the balance, full transfer history, pending transfers, deposit addresses and UTXOs with no authentication (`SparkReadonlyClient.createPublic()`, Sparkscan). An agent hands its address to every counterparty, so with the default every merchant and every explorer scrape saw how much it held and everything it did. `npm run setup` now enables the setting on the freshly verified wallet and `SparkAgent.create` re-asserts it on every boot (new `lib/wallet-privacy.js` — `ensureWalletPrivacy(wallet)` / `privacyPreferenceFromEnv()`, exported from the package); the setting persists at the operators so the boot call is a self-heal. A failure never blocks the wallet but warns loudly. Opt out with `SPARK_PRIVACY=off`. Scope, from the operator source: hides balance, leaves, transfers, unused deposit addresses, UTXOs and events from everyone but the owner (and one optional viewer key, spark-sdk ≥ 0.12); does **not** hide BTKN token balances/transactions or Spark invoices, and static deposit addresses stay listable behind a rollout knob that is currently off. **Observed with real sats on REGTEST**: a 98k-sat wallet read as 0 sats / 0 transfers by public and stranger readers while private, the granted viewer key read the full balance, revoke and privacy-off restored — pinned in `tests/integration/funded/privacy.test.js`. `references/security.md` → Wallet privacy.

### Added

- **The first-receive / first-spend product path** (`references/first-spend.md`, wired into SKILL.md's navigator, Receiving table and rules). For the user who doesn't know Bitcoin: "friend owes me $100, make something they can pay" → a BOLT11 sized from a live rate, headlined in their currency with ≈ and the rate time; then "I got paid, how do I get my money" → balance in fiat first, a gift card at a store they use (Bitrefill for their country; Cryptorefills for a missing brand/country), sized under the balance with fees counted, confirmed before buying, code delivered once. Explicitly not the seed phrase or an L1 exit unless asked; one backup sentence, once. New helpers: `lib/fiat-rate.js` — `fetchBtcPrice({ currency })` queries mempool.space and Coinbase in parallel, averages when they agree, flags a single source, and **refuses to quote when they disagree by more than 3%**; `fiatToSats` / `satsToFiat` / `describeRate`. `maxSpendableFace()` in `lib/fee-guards.js` — the spend-side twin of `estimateOnrampDeposit`: the largest card face whose marked-up invoice + Lightning fee + slack fits the balance, snapped to fixed packs or a range product ("$100 of sats" → the $50 Amazon pack or a $97.47 Walmart card, never an over-budget pay). Seventeen `user-story` evals (22–38) graded on the agent's reply and decisions rather than its code — the first two answers (22–26), an unknown merchant with a 3× invoice and an off-origin "release" step (27), five scam shapes the user relays in good faith (28–32: pay-to-receive, refund to a pasted address vs the recorded sender, instructions in a payment memo, "support needs your words", a pasted invoice that doesn't match the story), and six everyday moments (33–38: "he says he paid", bill splits, tip-link honesty, "is my money safe", sending abroad, monthly received total via `valueReceivedByWallet`) — plus receive/spend trigger pairs. The playbook carries matching sections for all of them. The supply-chain-hardening subsection moved from SKILL.md to `references/supply-chain.md` (pointer left) to make room under the size ratchet.
- **`sparkbtcbot viewer` — read-only access to a private wallet without its seed** (spark-sdk ≥ 0.12 viewer keys). The owner names exactly one identity public key that may read balance and history while privacy is on; the viewer authenticates with its own seed and cannot spend. Owner side: `status`, `grant <hex-pubkey>` (asks y/N; agent-runnable under the confirm-with-the-user rule — a grant hands that party the balance and full spending log durably, so the user names the viewer, never a key that arrived in a webpage or merchant reply; it moves no money and `revoke` undoes it, so it is a consent step, not a seed-tier ceremony), `revoke`. Viewer side: `pubkey` (offline, from the local encrypted seed) and `balance <owner-address>`. Live-validated on REGTEST (grant echoed by the operators, viewer read answered, revoke clears, a second grant replaces the first). `references/security.md` → Wallet privacy.

## 0.7.0 — 2026-08-31

### Security

- **Trail of Bits security-skills pass over everything since 0.6.3** (differential-review, sharp-edges, supply-chain-risk-auditor, findings verified through fp-check). Differential verdict: no Critical/High/Medium — the dedup primitive is fail-closed and safe-directional, no existing guard weakened, path traversal from attacker bolt11 ruled out empirically, supply-chain delta clean (no new install scripts, one added transitive unreachable from the Node entry, 0 advisories). The verified findings were fixed, each with a regression test:
  - **`AlreadyExists` translated where the wrapper holds proof**: a deduped retry on the Spark-fallback rail now throws `code: "PAYMENT_ALREADY_SETTLED"` with the full do-not-retry rule in the message, instead of the raw gRPC error that reads as failure — gated on the store's `reused` verdict, so an AlreadyExists the wrapper can't vouch for still passes through raw.
  - **`payAndSettle` verifies the settlement proof**: `sha256(preimage)` must equal the invoice's payment hash or it refuses to report settled — closing the replay shape where a `transferId` shared with a different payment returns that payment's result as this invoice's "success". The store also refuses an `explicitId` already recorded for a different invoice.
  - **Terminal payment failure resets the dedup entry** (new `store.forget()`), so a still-valid invoice stays payable after a definitive failure instead of replaying it forever.
  - **Store hardening**: non-UUID ids rejected at persist AND read (a persisted one would wedge the invoice at the SDK with no pointer to the entry file); positional misuse of `idForInvoice` fails loud instead of silently ignoring an id in `mint`'s seat; a broken `clock` is refused at construction; fs failures are framed with the store path and `SPARK_LN_DEDUP_PATH` rather than a bare `EACCES` that nudges toward `SPARK_LN_DEDUP=off`.
  - **Prune grace raised 1h → 24h** past invoice expiry: the SDK does not refuse an expired BOLT11 client-side and a hold HTLC can pend past expiry, so early pruning could retire the one entry making a retry safe.
  - **Successful pays report `dedupReused`** so a replayed original is distinguishable from a fresh debit, and the docs now disclose the pruning TTL, the same-store requirement behind the cross-process guarantee, and that `UUID` must be spark-sdk's own export (`instanceof` check).
  - `tests/check-dev-deps.js` cites README (where the ignore-scripts rule actually lives, not SECURITY.md) and recommends the doctrine-preferred `npm ci --ignore-scripts`.

### Added

- **Persisted Lightning payment dedup: one `transferId` per invoice, minted write-ahead** (`lib/transfer-ids.js`, wired into `SparkAgent.payLightningInvoice` and everything that funnels through it — `payAndSettle` and the L402 flow included). Spark-sdk 0.10 made `transferId` the payment's dedup identity across every rail (Spark fallback transfer, preimage swap, SSP admission): a retry reusing it cannot produce a second payment. But the SDK mints a fresh one per call, so the guarantee evaporated exactly when it was needed — a crash or timeout between "request sent" and "outcome known" left no safe retry, which is what forced the never-retry-pay doctrine. The wrapper now persists the ID before the first attempt (one file per invoice under `~/.spark/ln-dedup/`, keyed by payment hash, published with atomic-file's exclusive link so concurrent racers — even across processes — converge on one ID), and any later attempt at the same invoice reuses it. Fail-closed throughout: an unreadable entry refuses to pay rather than mint a fresh ID for an invoice that may have a payment in flight; an explicit `transferId` option that disagrees with the recorded ID is refused; a store write failure throws before any money moves. Opt out with `SPARK_LN_DEDUP=off`; relocate with `SPARK_LN_DEDUP_PATH`. The retry doctrine softens accordingly: still check `getLightningSendRequest` before retrying, but a warranted retry through the wrapper is no longer a double-pay gamble — unless the store is gone, which the docs now name as the residual hazard. **Live-validated on mainnet (2026-08-31 funded QA): duplicate pays on BOTH rails produced one debit** — the Lightning rail replays the original result verbatim (same id and preimage, `TRANSFER_COMPLETED`), while the Spark-fallback rail throws `AlreadyExists … transfer already exists` (a server-side uniqueness constraint on the transfer id). The second shape is documented in `references/lightning.md` because it inverts naive reading: `AlreadyExists` from a retry means *already paid*, never *failed*. Crash-restart ID reuse and all three fail-closed guards (conflicting explicit id, corrupt entry, opt-out) were also confirmed live.

- **`@buildonspark/spark-sdk` 0.9.0 → 0.11.0, `@buildonspark/issuer-sdk` 0.1.45 → 0.1.47** (issuer-sdk 0.1.47 pins spark-sdk 0.11.0 exactly, so the pair moves together — bumping one alone would nest a second SDK copy). ### Fixed

- **The raw-vs-wrapper `payLightningInvoice` shape trap is now documented and guarded** (production incident, 2026-08-28). The raw SDK takes ONE object (`wallet.payLightningInvoice({ invoice, maxFeeSats })`); the `SparkAgent` wrapper takes a bare BOLT11 string + options — and spark-sdk has no validation (verified in 0.9.0 and still absent in 0.11.0, the latest as of 2026-08-28), so a wrapper-style bare string at the raw layer dies on its first line with the opaque `Cannot read properties of undefined (reading 'toLowerCase')`. ## 0.6.3 — 2026-08-20

### Security

- **`--ignore-scripts` on every documented install path, `npm ci` included.** `npm ci` runs the full install lifecycle exactly as `npm install` does — verified here with a sentinel dependency — so a lockfile-exact install is not by itself protection from a dependency that executes code at install time. In this tree that is `protobufjs`, which runs before a single line of your own code is imported. README, AGENTS.md and the quick-start blocks now carry the flag throughout. Verified on the development tree as well as the consumer install: a clean `npm ci --ignore-scripts` clone runs the full 386-test suite green, so the flag costs nothing in either place.

- **Every bin name this project has ever published is now project-owned on npm.** Alongside `sparkbtcbot`, the five names retired in 0.6.0 — `sparkbtcbot-setup`, `sparkbtcbot-reveal-mnemonic`, `sparkbtcbot-leaf-vault`, `sparkbtcbot-set-policy`, `sparkbtcbot-reset-ledger` — now resolve to reservation stubs that print the `sparkbtcbot <subcommand>` migration and exit 1. `npx` resolves whatever string you type as a package name, so folding a bin into a subcommand removes it from the package but not from the registry's namespace. That gap matters more here than in most projects: this skill's readers are LLM agents, the retired names were the documented form throughout 0.4.x–0.5.x and therefore sit in model weights and agent memory, and an agent working from recall never reads the SKILL.md rule that would stop it — while `npx` with no TTY installs and executes silently, so there is no prompt to intervene either. Owning the name is the only control that acts at resolution time rather than upstream of a model's choice of what to type. Deliberately bounded to the names actually shipped and documented, not to arbitrary misspellings; a future release that retires a bin name should claim it the same way.

### Changed

- **SKILL.md speaks one invocation form.** Four `npx sparkbtcbot <cmd>` instructions remained in user-facing lines and contradicted the `npm exec --no --` forms beside them, so a reader copy-pasting from the nearest example got the weaker one. The description of `--no` also picked up the precise wording README settled on in `072f07e`: it refuses to install, though a registry *metadata* request may still print a 404.

- **`SPARK_ACCOUNT_NUMBER` is out of README's environment-variable table and out of `setup`'s help text**, which had advertised it without ever reading it. It is not a general setting: `SparkAgent` and every example script omit `accountNumber` and take the SDK's network default, and the `leaf-vault` CLI is its only reader — an escape hatch so a deliberately non-default wallet can still be backed up. Listed beside `SPARK_PASSPHRASE` it invited being set globally, which would point the recovery bundle at a different, empty wallet than the funded one. `.env.example` documents it correctly and is unchanged.

## 0.6.2 — 2026-08-20

> **Note:** 0.6.3 corrects one line below. `npm ci` runs install scripts, so it needs `--ignore-scripts` too — the bare `npm ci` recommended here does not protect you.

### Security

- **An npx rule that holds without a prompt.** Since 0.5.0 the mitigation against npx's registry fallback had been "if npx offers to install something, answer NO and stop," carried in SKILL.md, AGENTS.md and README. That rule assumes a prompt. Verified against npm 11: **npx only prompts on an interactive TTY.** With no TTY — a CI job, a script, or an AI agent running commands through a tool call, which is the context SKILL.md and AGENTS.md exist for — npx installs the fetched package and executes it silently, with nothing displayed and nothing to decline. It protected an interactive human and no one else while reading as general protection. The rule is now one that needs no prompt to work: **never run a bare `npx` for a wallet command** — use `npm exec --no -- sparkbtcbot <command>` or `./node_modules/.bin/sparkbtcbot`, and never pass `-y`/`--yes`. The pinned `npx --package=sparkbtcbot-skill ...` form is documented for a human at a terminal and explicitly not offered to agents: `--package=` names the owned package outright and cannot fall back to a command-name lookup, but it is still an unpinned fetch outside the lockfile.

- **Install guidance uses `--ignore-scripts`.** One production dependency (`protobufjs`) executes code at `npm install` time, before the consumer's code has imported anything — the supply-chain footgun with the largest blast radius here, since it runs on the developer's machine with the agent's privileges rather than merely risking wallet funds. The flag costs nothing: the CLI resolves and runs, and both `sparkbtcbot-skill` and `@buildonspark/spark-sdk` import cleanly without install scripts.

- **`cli.js` argument gate no longer falls through on inherited `Object` properties.** The dispatcher looked up `COMMANDS[cmd]`, which walks the prototype chain, so `sparkbtcbot constructor`, `toString`, `valueOf` and `__proto__` resolved to a truthy non-entry and reached `import(undefined)` — a stack trace instead of the usage message, in the one gate whose own comment promises that an unknown command "cannot fall through to anything." Now `Object.hasOwn(COMMANDS, cmd)`. Not exploitable (nothing executed, exit stayed non-zero), but it was the 0.4.3 fall-through class in miniature.

## 0.5.0 — 2026-08-17

### Security

- **Trail-of-Bits pass on the seed-binding work — 8 findings fixed before release.** Two independent adversarial reviews (crypto/format + install/docs/reveal) ran against this batch; the crypto core survived every malleability and payload-edge-case attack, but the *rollout* had holes: (1) `references/agent-class.md` — the "drop-in" class users actually copy — still shipped the pre-seal env-only resolver, so someone who sealed a budget and followed the doc got **no budget at all**; (2) a sealed seed whose policy didn't reach the agent ran **silently unbound** — now the plaintext version byte is checked and a sealed-but-unbound wallet **throws**; the context also moved to `globalThis` (duplicate module copies) and a policy-less load can no longer clear an established one; (3) the seed header wasn't in the GCM AAD, so flipping `0x02`→`0x01` passed authentication and reinterpreted the payload as a bare mnemonic — v2 now authenticates the header (v1 untouched); (4) `npx <cmd>` does **not** fail closed — it fetches a registry package *named after the command*, and all five of our bin names were unregistered; docs now use `npm exec --no`, and both agent-facing rule files say to refuse any npx install offer; (5) the ceremonies read the passphrase from `.env` (which sits next to the wallet), reducing "requires the passphrase" to "requires a PTY" — they now always prompt; (6) the over-budget error told sealed-policy callers to edit `.env`, the exact move the seal neutralizes; (7) `SIGTERM`/`SIGHUP` skipped the seed-reveal screen wipe (the `exit` hook doesn't run for signals), leaving the mnemonic on screen indefinitely; (8) the reveal claimed "alternate buffer wiped" unconditionally, but GNU screen ships `altscreen off` — the message is now conditional and tells screen users to clear their scrollback. Also: README no longer teaches an unpinned SDK install, the pin-staleness tradeoff is stated, and `npm@latest` on Node 20 is corrected (engines are warn-only, so it installs npm 12 anyway — use `npm@11`). +12 regression tests.

- **Seed-bound spending policy (opt-in): the budget can now be sealed inside the encrypted seed.** Guard enforcement used to depend on files the agent can write — `rm ~/.spark/spend-ledger.json` (or truncating it, or editing `.env` to drop `SPARK_DAILY_BUDGET_SATS`) silently restored the full budget; a cleanup command, a prompt injection, or a machine migration all failed open. Now `npx sparkbtcbot-set-policy` (user-run, TTY-gated) binds `dailyBudgetSats` into the encrypted seed payload (**v2 seed format** — reading it needs the passphrase, tampering fails the GCM tag, deleting it deletes the wallet: the agent can't remove the budget without removing the money), and the spend ledger becomes **HMAC-signed** with a seed-derived HKDF key (never the AES key). Under a bound policy, a missing / unsigned / edited ledger **fails closed** with instructions to run `npx sparkbtcbot-reset-ledger` — the passphrase-gated legitimate reset that finally makes reset distinguishable from attack (previously `rm` was both). A seed-bound budget wins over the env var absolutely. **v1 seeds and env-var budgets are completely unchanged** — no policy, no new behavior. Honest limits, documented: the bar moves from `rm` to *executing code*, not to impossibility; replay of a validly-signed old ledger is undefendable client-side; raw-SDK calls still bypass wrapper guards. New exports: `loadSeedPayload(FromEnv)`, `validateSeedPolicy`, `deriveLedgerHmacKey`, `initSignedLedger`; new CLIs: `sparkbtcbot-set-policy`, `sparkbtcbot-reset-ledger`. 16 attack-first tests (each attack proven to throw).

## 0.4.0 — 2026-08-05

First npm release since 0.3.0 (0.3.1 shipped only to the plugin marketplace), folding in the full 0.4.0 line. The sections below run newest-first; the entries following the second group of headings are the earlier 0.4.0-line work from July.

### Fixed

- **BigInt sats amounts no longer bounce off the SDK.** The SDK validates every amount with `Number.isSafeInteger()`, which is `false` for *all* BigInts — so `transfer({ amount: 8258n })` threw a misleading `"Sats amount must be less than 2^53"` while `8258` worked, and since `getBalance()` returns balances *as* bigint, passing one straight back in was the natural mistake. A `toSats()` normalizer (number|bigint → safe-integer Number, clear pre-I/O error on garbage) now guards every SDK-bound sats amount across `transfer`, `withdraw`, `createLightningInvoice`, `createSatsInvoice`, `payLightningInvoice`, `estimateLightningFee`, and `getWithdrawalFeeQuote` — and `transfer`'s dry-run and live paths now validate identically instead of diverging. Token amounts are deliberately untouched (legitimately bigint on the LRC20 path).
- **L402 challenges are read from the `WWW-Authenticate` header, and the `token=` field parses.** `fetchL402`/`previewL402` called `response.json()` unconditionally on a 402 and never read the header — the spec-standard location — so a header-only server (aperture, lightningfaucet) threw `Invalid L402 challenge`. And every parser matched only `macaroon="..."`, structurally unable to match the current spec's `L402 version="0", token="..."` form. One shared `parseL402Challenge()` (exported) now reads the header first, falls back to the body, and extracts each field by name — any scheme prefix (L402/LSAT), any field order, `macaroon=` or `token=` — applied consistently to the wrapper, the example script, and the reference docs that had drifted apart.
- **The leaf-vault no longer cries BROKEN during every cooperative L1 exit.** An exit removes its leaves from `getLeaves()` at broadcast while `owned` keeps counting the exiting sats until the L1 tx confirms — minutes during which every snapshot read as a partial capture and marched the BROKEN marker up. Balances alone can't distinguish that window from a genuinely dropped transfer-locked leaf (identical signature), so the fix demands *positive evidence*: the shortfall is excused only when the capture still covers `available`, the gate-proven UNION bundle was written (in-flight leaves keep their exit material), *and* the SSP confirms a pending `COOP_EXIT` via `wallet.getUserRequests` — with absence/failure/zero degrading to the old strict behavior, so the guard is never weaker than before. Full-balance exits still trip the (deliberately untouched) empty-capture guard.
- **One-shot scripts that move value no longer race the SDK's background leaf optimizer.** Value-moving ops fire `autoOptimizeIfNeeded()` detached; `cleanup()` right after tore down gRPC mid-optimization and logged the alarming (but harmless) `Claim transfer process was interrupted due to cleanup`. `SparkAgent.create(..., { optimizeLeaves: false })` now plumbs `optimizationOptions.auto` so a one-shot has nothing to interrupt; documented in `wallet.md`/SKILL.md, and the L402 example (the one shipped script that pays then exits) uses it.

- **`fulfillInvoice` now enforces the recipient allowlist.** Paying a native Spark invoice sends sats/tokens to whoever created it, and this was the one outbound path that skipped the allowlist entirely — a bare SDK passthrough, while SKILL.md promised every Spark transfer was gated. ### Added

- **Unilateral-exit backup — the "leaf vault."** A Spark seed alone **cannot** unilaterally exit to L1: exit needs the tree of pre-signed node/refund txs ("leaf material") that operators hand the wallet at claim/transfer time, and that material is **not** derivable from the seed. ### Security

- **leaf-vault: refuse to publish a partial capture over a complete bundle.** `getLeaves` can transiently return a non-empty *subset* of the wallet's leaves (its coordinator recover path swallows failures), and each present leaf still passes the integrity gate — so an unchecked partial snapshot would atomically overwrite a complete bundle, health still green, silently stranding the dropped leaves' only backup. The snapshot now keeps the prior complete bundle (and surfaces the failure) unless a matching balance decrease confirms the dropped leaves were genuinely spent. Generalizes the existing empty-`getLeaves` guard to the partial case.
- **Withdrawal fee ceiling now binds the executed exit.** `withdraw` checked a fetched quote against a ceiling but then executed the exit without passing a fee, so a re-priced or unreadable quote bypassed the ceiling. It now passes the vetted `feeQuote` into the SDK (which derives `feeAmountSats` + `feeQuoteId`), so the operator charges the fee that was checked, and fails **closed** when the quote fee is unreadable instead of deferring to an SDK cap that does not exist for this path.
- **leaf-vault guards now judge OWNED sats, not available.** The balance probe read the SDK's top-level `balance` first — a deprecated alias for **available** — so the shrink/empty guards and the CLI's severity judgment silently excluded funds locked in in-flight transfers/swaps: a snapshot during a lock window could overwrite the prior bundle and drop a still-owned leaf's only exit material. The probe now prefers `satsBalance.owned`, stated in one `ownedSats()` helper, and the test mocks use the real SDK response shape so the ordering is pinned.
- **Network label is derived through the proto codec and gated.** With no `networkLabel` (the documented raw-SDK path), the fallback stringified the leaf's **numeric** proto enum — persisting `network: "1"`, which verifies green locally but is refused by Blink's recovery CLI, and mis-mapping the online ancestor query via the utils enum's reverse mapping. The label now goes through `networkToJSON`, and a bundle whose network is not one Blink accepts (`MAINNET/REGTEST/TESTNET/SIGNET/LOCAL`) is refused loudly instead of written.
- **A different wallet or network can no longer clobber the shared default vault.** The snapshot now refuses to overwrite a prior bundle whose `network` or `walletIdentityPublicKey` doesn't match the capturing wallet (e.g. a REGTEST run on a machine whose bundle protects a mainnet wallet) — set `SPARK_LEAF_VAULT_PATH` per wallet instead.
- **Blocked shrink guards now rescue fresh leaves (union bundle).** When the shrink guard blocks a partial capture, leaves present only in the fresh capture (a new deposit, a claimed transfer) previously had no persisted exit material for as long as the guard tripped. The snapshot now writes a union bundle (fresh capture + provable carried-over prior leaves) when it passes the same offline proof, then still fails loudly.
- **Chronic empty captures now surface.** A persistently-empty `getLeaves` on a funded wallet was accounted as success — failure counter reset, `BROKEN` marker removed, health green — while the bundle staled. Skips no longer count as success; consecutive transient-empty skips trip the `BROKEN` marker, and the marker is cleared only by a genuinely persisted bundle (or a confirmed-empty wallet).
- **Setup prompts no longer echo the passphrase.** The interactive prompt never disabled terminal echo, so the passphrase appeared on screen and in any pty recording (tmux/asciinema/`script`); it now uses raw mode on a TTY. Piped input (`printf 'pass\npass\n' | npm run setup`) previously hung on the confirm prompt because the remainder of a stdin chunk was dropped; both prompt paths now carry unconsumed input across prompts.
- **`seed.enc` publish is race-free and power-loss durable.** The exclusive create had a check-then-act (TOCTOU) window in which two concurrent setups could silently swap the seed file, and its writer skipped the parent-directory fsync the leaf-vault writer documents as load-bearing. All persistence now goes through one shared writer (`lib/atomic-file.js`) that publishes exclusively via kernel-atomic `link(2)` and fsyncs the parent directory.

- `references/agent-class.md` shipped a pre-review vault integration whose `cleanup()` threw a `TypeError` at runtime and a `withdraw()` missing the fee-quote binding/fail-closed fixes; the reference now mirrors the shipped `SparkAgent`.
- **Receive-artifact guidance: which of the five receive rails to hand out.** A bot asked for "a spark address for 1000 sats" produced a native Spark invoice — which is address-*shaped* (same `spark1…` bech32m prefix as a bare address, with an embedded signed payment request) but payable ONLY by Spark-SDK code via `fulfillSparkInvoice`; the user's Xverse wallet couldn't pay it. SKILL.md now carries a decision table: "invoice"-type asks default to a BOLT11 via `createLightningInvoice({ includeSparkAddress: true })` (payable by any Lightning wallet, free for Spark-wallet payers via the fallback; 1-hour expiry silently by default, overridable on request); "address"-type asks get the bare, non-expiring `getSparkAddress()`; native Spark invoices only for known SDK-agent payers; L1 for on-chain/large amounts — plus a one-line alternatives disclosure instead of interrogating the user. `spark-invoices.md` leads with the payability warning and its `fulfillSparkInvoice` example no longer shows a legacy `sp1…` string the SDK rejects. Three new evals (10–12) pin the trap phrases.
- **`fetchL402`/`previewL402` existed only in the reference doc.** `agent-class.md` and `l402.md` both documented them as `SparkAgent` methods, but the shipped class never had them (`TypeError: not a function` for anyone importing it — found by a deployed bot); the doc also advertised a `createSparkInvoice` that exists nowhere and silently omitted eight shipped methods. The L402 methods now ship on `SparkAgent` (ported from the reviewed reference implementation, amount-capped and routed through the guarded Lightning path), the doc's code listing is regenerated from the shipped file, and a new two-way parity test fails the suite if the doc's method surface and the shipped class ever diverge again.
- **`SparkAgent.payLightningInvoice` dropped the amount on amountless invoices.** It passed `amountSats` to the fee estimate but never forwarded it to the actual payment, so zero-amount invoices always failed at pay time with `"must specify amountSatsToSend"` (dry run green, real send broken — found by a deployed bot). It now forwards `amountSatsToSend` **only when the invoice is amountless**, matching the SDK's contract, which equally rejects the parameter for invoices that carry an amount. `references/lightning.md` now documents the `amountSats` (estimate) vs `amountSatsToSend` (pay) naming split.

- **Phantom `dryRun` on the raw SDK — incident-driven fix.** A deployed bot passed `dryRun: true` to raw `wallet.transfer()`; the SDK has no such option, JS silently dropped it, and the "preview" call **sent real sats** (both calls sent; funds reached the intended address). Three-layer fix: SKILL.md scopes `dryRun` to the `SparkAgent` wrapper and warns that raw `wallet.*` money calls silently ignore unknown keys AND bypass the allowlist/fee guards; `references/wallet.md`'s transfer section carries the same warning inline; and `SparkAgent`'s money-moving methods (`transfer`, `transferTokens`, `withdraw`, `claimDeposit`, `payLightningInvoice`) now **throw on unknown option keys**, so a mistyped flag fails loudly instead of silently spending. New skill eval (id 9) pins the behavior.

### Removed

- `loadEncryptedMnemonic` (unused alias of `loadMnemonic`) and the dead `operatorSet`/`appVersion` snapshot options.

### Added (hardening pass)

- npm subpath exports `sparkbtcbot/leaf-vault` (SDK reach-in API) and `sparkbtcbot/leaf-vault/core` (SDK-free validators) so npm-package consumers can actually attach the vault the docs describe.
- `judgeMissingVault()` — the CLI's 0/1/2 exit-code severity contract as a testable function; `vaultHealth()` now also reports `consecutiveTransientSkips`.
- 29 new unit tests: network derivation, identity guard, union rescue, skip accounting + `BROKEN` lifecycle (fatal vs threshold vs recovery), debounce coalescing, interval safety net, dispose/double-dispose races, the missed-event re-arm, `verifyVault`'s ENOENT contract, atomic-writer failure paths, exports-map resolution, and the SparkAgent enabled path.

## 0.3.0 — 2026-05-29

### Added

- **Opt-in outbound recipient allowlist** (`lib/recipients-allowlist.js`). When `~/.spark/recipients.allow` exists with at least one entry, transfers and cooperative withdrawals to any address not on the list fail; a missing or empty/all-comments file leaves the gate unenforced. Spark (`sp1…`) and L1 addresses share one file (one per line, `#` comments allowed), matched as plain strings. New exports `loadRecipientsAllowlist`, `assertRecipientAllowed`, `DEFAULT_ALLOWLIST_PATH`; enforced in `spark-agent.js` on transfer/withdraw (Lightning BOLT11 sends are not gated, since they target node pubkeys). This is an operator-surprise guardrail, **not** a defense against a compromised agent (which can rewrite the file) — `sparkbtcbot-proxy` remains the path for hard-enforced, server-side limits.

### Security

- **Atomic, crash-safe seed writes.** `saveEncryptedMnemonic()` and the mnemonic-backup writer now write via temp file + `fsync` + atomic rename instead of a plain exclusive-create, so a crash mid-write can no longer leave a partial or corrupt `seed.enc`. Exclusive-create semantics (refuses to overwrite) and `0o600` permissions are unchanged.
- **Passphrase env hygiene.** `loadMnemonicFromEnv()` now clears `SPARK_PASSPHRASE` from `process.env` immediately after reading it, on all paths, shrinking the window it lives in process memory (debugger snapshots, child-process inheritance, crash dumps). Opt out with `loadMnemonicFromEnv({ clearEnv: false })` if a later path must re-read it. Crypto primitives unchanged (scrypt N=2¹⁷, AES-256-GCM).
