# Changelog

## 0.9.0 — 2026-10-27

spark-sdk 0.14 with the SDK's fee ladders forced off, and the money paths hardened against what three review rounds and a day of real REGTEST payments turned up: an expired invoice that locks the payer's coins, a single-use deposit the operators won't claim, a paywall retry that buys twice, a forged ledger entry that empties a sealed budget. Each fix below names the failure it closes, and the funded REGTEST tier now pays real invoices end to end, a local L402 server included.

### Upgrading from 0.8.0

- **`getSingleUseDepositAddress()` throws** (`SINGLE_USE_DEPOSITS_UNAVAILABLE`): the operators refuse to claim single-use deposits. Use `getDepositAddress()`. Coins already sent to a single-use address show in `listPendingDeposits()` as `type: "single-use"`; they arrived but can't be claimed now.
- **`claimDeposit` checks the deposit itself**: it claims only a deposit at the static address (`DEPOSIT_NOT_FOUND`, `DEPOSIT_LOOKUP_INCOMPLETE`), the default fee ceiling stops at 25,000 sats, and `maxFeePct` must be 0–100.
- **`payLightningInvoice` refuses** an expired invoice (`INVOICE_EXPIRED`), and an invoice with two payment hashes or a malformed one.
- **More failures are `PAYMENT_COMMITTED`**: any error that doesn't prove nothing was sent. Treat it as "the money may have left": never pay again with a new invoice, address or method; check `getTransfers()` (token sends: `getTokenTransactions()`).
- **`fetchL402` stops on a refused or doubtful purchase**: that URL is blocked in the process until `forgetL402(url)`, on the user's say-so. A POST is re-sent only with `{ resend: true }`.
- **Importing `sparkbtcbot-skill/agent` no longer loads `.env`**: add `import "dotenv/config"` to your app.
- **A payment bound to a payment hash goes over Lightning**, never Spark-direct; `preferSpark: true` with `expectedPaymentHash` throws.
- **Opening wallets yourself?** Pass `sparkWalletOptions()` so the fee ladders stay off; SDK 0.13+ turns them on by default.
- **Additions**: `createTrackedInvoice` / `getInvoiceStatus`, `getTokenTransactions` / `getTokenTransaction`, `getBalance().lockedSats`, `feeSats` on Lightning results, the time window on `getTransfers`, and the `sparkbtcbot-skill/agent` export.

### Security

- **A forged spend-ledger entry can no longer hollow out a sealed budget.** `set-policy` signed an unsigned, agent-writable ledger as it stood, and the validator accepted a negative or fractional entry, so one planted `{ sats: -15000000 }` let 15,000,000 sats through a sealed 20,000-sat budget. Entries must now be non-negative whole sats everywhere a ledger is read, written or signed (`record()` rounds a fractional amount up; it used to write one that every later read rejected). `set-policy` also treats a missing or unsigned ledger under an already-sealed budget as tampering (nothing changes; `reset-ledger` is the deliberate path), and re-checks the ledger before it rewrites the seed rather than after. This regression came in with the earlier `set-policy` port on this branch; found by the Trail of Bits review of 2026-10-26.
- **`fetchL402` no longer pays twice when the payment itself fails ambiguously.** If the pay call threw `PAYMENT_COMMITTED` or `PAYMENT_ALREADY_SETTLED`, or a status read threw while `payAndSettle` waited, nothing was held, so the documented "call again" bought a fresh invoice. Now the purchase is held and the next call settles that same invoice through the dedup store (with `SPARK_LN_DEDUP=off` it refuses and says to check transfers), and a failed status read is treated as no news. Also: a 408 or 429 on delivery is retried with the same pass; a POST or PATCH is presented once, never re-sent; a 401/402 after paying throws `L402_PASS_REFUSED` instead of returning the server's new challenge as data; the minimum token lifetime is 120 s (it was 60, the whole polling window); `maxAmountSats` reaches the payment.
- **Importing `sparkbtcbot-skill/agent` no longer loads the host app's `.env`.** The module ran `import "dotenv/config"`, so a planted `./.env` could switch off dedup, the backup or privacy, or set `NODE_TLS_REJECT_UNAUTHORIZED=0` for the `fetch` paths. Only the runnable demo loads dotenv now; a test pins it.
- **Merchant strings never reach a shell as text** (`merchant-spending.md` §1a, mirrored in `bitrefill.md`, `cryptorefills.md`, `nadanada.md`, `l402.md`). The shipped code never shells out; the injection surface is the agent composing a command line — Bitrefill's CLI `--cart_items`, a `curl` against a directory URL, nadanada's REST — from catalog values. Rule: prefer MCP/JS over a CLI; when a CLI is the path, argv arrays or a JSON file, validate ids (`^[A-Za-z0-9][A-Za-z0-9._-]*$`, no `..`) and URLs (`https://`, plain host) first, never interpolate, never `eval`/`sh -c`, never `echo` a code into a pipeline. Eval 13 gains the assertion; new eval 39 hands the agent a product id shaped like `x'; curl … | sh; '`. The rule treats every seller-controlled field as hostile.
- **A merchant checkout's payment-hash check now holds when the invoice carries a Spark fallback.** `SparkAgent` pays an invoice from a Spark wallet Spark-direct: a plain transfer to the fallback key, free, with no preimage. That transfer ignores the payment hash, so the merchant helper's check (the invoice must carry the hash the checkout echoed) protected nothing on that route. A fallback added to the merchant's invoice keeps its hash, amount and description, since the SDK checks the signature only when the invoice has an `n` tag. Any Spark user can also get a properly signed invoice that carries a hash they choose and their own fallback. `payLightningInvoice` and `payAndSettle` now take `expectedPaymentHash`: the wrapper refuses an invoice without that hash before anything is sent, then pays over Lightning, where the payment completes only against that hash's preimage. `preferSpark: false` turns Spark-direct off without a binding, and the dry-run preview reports which applies. `payMerchantCheckout` (`references/merchant-spending.md`) passes both, so merchants are always paid over Lightning; every other payment keeps Spark-direct. Tested through the real SDK `payLightningInvoice` with a fallback spliced into a signed invoice, and on REGTEST, where a Spark wallet's invoice settled Spark-direct unbound and over Lightning, with a preimage matching the hash, when bound.
- **An invoice with two payment hashes no longer passes the hash check.** `invoicePaymentHash` read the first `p` field and the SDK pays under the last, so an invoice carrying the checkout's hash and then another passed `paymentHashMatches` and paid under the other. It now returns null unless the invoice has exactly one 32-byte payment hash, and the check fails.
- **`fetchL402`'s second call, after a payment that may have gone through, is safe to make.** Every error on that path is now `PAYMENT_COMMITTED`; before, a raw `"exceeds available balance"` (likely because the first payment went through) read as "nothing was sent". Settling the held invoice again no longer counts against the budget a second time (one 2,000-sat purchase used to fill a 10,000-sat budget in five calls). It re-reads the token first and won't pay for a pass the service has declared dead. Three outcomes stop the purchase for good in that process, each a `PAYMENT_COMMITTED` with a `reason`: the service refused the paid pass (`L402_PASS_REFUSED`, which was a plain error that forgot the purchase, so a retry loop bought again), the pass died first (`L402_PASS_EXPIRED`), or the payment ended with no proof (`L402_NO_PROOF`, which used to read as "still pending" forever). `agent.forgetL402(url)` lifts it, on the user's say-so. A POST or PATCH that may have reached the service is sent again only with `{ resend: true }`; "call again" used to place a second order on the same pass.
- **An invoice whose one payment hash isn't 32 bytes is refused before paying.** It passed the two-hash check, read as having no hash, and the preimage check then accepted any preimage.
- **`claimDeposit`'s default fee ceiling stops at 25,000 sats**, and `maxFeePct` must be 0–100 (also on `withdraw`). 10% of a 0.49 BTC deposit allowed a 4,900,000-sat fee against a spread of a few hundred, and `maxFeePct: 1000` was accepted. An explicit `maxFeeSats` still goes past the cap.
- **`payLightningInvoice` refuses an expired invoice before the SDK sees it.** Paying one through the raw SDK doesn't just fail: on hosted REGTEST the SDK moved 303 sats into a transfer to the SSP, the SSP then refused the send, and the transfer sat at `SENDER_KEY_TWEAK_PENDING`, expiry 16 days out, with no way to cancel it, until the SSP returned it about an hour later (REGTEST; mainnet untested, and Spark's docs promise no return time). `SparkAgent` now throws `INVOICE_EXPIRED` for an invoice that has expired or has under 30 seconds left, before any SDK call (so `payAndSettle`, `fetchL402` and the merchant helpers refuse it too). Spark documents the lock ("Check expiry before paying": the SDK doesn't check expiry before the swap, and the 16-day expiry "is not a guaranteed refund time"). When the dedup store holds an earlier attempt at the same invoice, the refusal is a `PAYMENT_COMMITTED` (`reason: "INVOICE_EXPIRED_AFTER_ATTEMPT"`; a different word from the plain refusal's `code: "INVOICE_EXPIRED"`, so code that checks either can't mix them up) instead: the retry an unclear outcome invites would otherwise have said "ask for a new invoice", and paying that would have been a second payment. In `fetchL402`'s retry the same case is a block, `L402_INVOICE_EXPIRED`. An attempt that provably sent nothing (refused by the spend budget, or by the SDK before sending) no longer leaves a dedup entry behind to read as an earlier attempt later, and the plain refusal says to check `getTransfers()` first if an earlier attempt's outcome was unclear (it can't know once the store has pruned the entry, or with dedup off). The raw-SDK example script and the `l402.md` and `lightning.md` snippets check the expiry before paying, and `getBalance()` reports `lockedSats` (owned minus available), so locked sats read as locked rather than missing.
- **`fetchL402` never drops anything it holds.** The held map dropped its oldest entry at 100, so 100 other holds later a refused URL, or a purchase that may have paid, was bought again on nobody's say-so. Nothing held is dropped now; at 1,000 unresolved purchases in one process, a new one is refused before paying. A block's error now names the call that lifts it (`forgetL402(url, { method: "POST" })` for a POST) and carries the invoice hash and amount, and `{ resend: true }` refuses a body that differs from the request it re-sends.
- **No instruction tells you to run bare `npx sparkbtcbot …`.** Run from a directory without the package installed, bare `npx` fetches whatever the registry has under that name and runs it, with no prompt in a non-interactive shell, and these commands (`reset-ledger`, `set-policy`) run next to the seed with the passphrase. The runtime errors that agents copy literally (`lib/spend-ledger.js`, `spark-agent.js`), `security.md`, `encrypted-seed.md` and three eval assertions now say `npm exec --no -- sparkbtcbot <command>`. The README no longer calls the retired command names unclaimed (they are project-owned stubs that refuse and explain) or says `--no` means nothing runs: it refuses only to install, so a cached, global or parent-directory copy still runs; run from the project or call `./node_modules/.bin/sparkbtcbot`. A docs-lint rule fails on any bare `npx`, `npm exec` or `npm x` without `--no` before a `sparkbtcbot` command in docs, evals and sources (#14). Evals 7, 19, 20 and 36 haven't been re-run since their assertions changed.
- **The publish workflow runs no dependency code where the publishing token lives.** One job held `id-token: write` while `npm ci` and `npm test` ran the whole dev tree (vitest, vite, a native rolldown binary), so a compromised dev dependency could have rewritten a file between checkout and `npm publish`, and the provenance attestation would have vouched for it. Now a `test` job with read-only permissions installs, hardens and tests; a separate `publish` job checks out the same commit, installs nothing, checks the tree is untouched and publishes. npm is pinned (11.21.0) instead of `@latest`, which ran before the hardening step and so was never age-gated.

### Changed

- **spark-sdk 0.12.0 → 0.14.0, issuer-sdk 0.1.48 → 0.2.1, with the SDK's fee ladders turned OFF.** Nothing this package calls was removed or changed shape; the APIs 0.13 and 0.14 dropped (`queryTokenTransactions`, the V2 token path, the `start_transaction`/`commit_transaction` RPCs) were never used here. What the upgrade brings: 0.12.1 fixes `getBalance` reading **zero sats with no error** after a session token expired on a non-coordinator operator; 0.14 adds amountless-invoice Lightning quotes and silent-payment (`sp1q…`) withdrawals, neither wired into `SparkAgent`. What it would have changed without this release: 0.13 turns on two fee ladders by default. With the refund ladder, each claim gives a leaf of about 1,024 sats or more a refund with no anchor and no fee, and hands the operators up to 24 fee steps signed with the leaf key; the top step leaves the owner 330 sats. The node-hop ladder signs fee variants of the direct transaction when a refund timelock is renewed. On hosted REGTEST every step verified as a fully signed, broadcastable transaction, and every claim sent a new set. A leaf-vault backup holding one anchorless refund fails as a whole in the exit tool it is made for, and the operator code that stores and publishes the steps isn't public yet. So every wallet this package opens now passes `sparkWalletOptions()` (new, exported with `FEE_LADDERS_OFF`), which forces both options off whatever else is passed: `SparkAgent`, `setup`, `leaf-vault`, `viewer`, the example scripts, the test helpers, and every `initialize` snippet in SKILL.md and the references. A test fails if a call site in the scripts, the references, SKILL.md, README or AGENTS.md skips it, or if any of them writes wallet options as a raw object, prose included (a SKILL.md sentence on one-shot scripts did, and turned both ladders on). `SparkAgent` warns at construction when it's handed a wallet that was opened with a ladder on. The options belong to the wallet object, so code that opens the seed through the raw SDK must pass them too (`unilateral-exit.md` → fee ladders). Off is reversible; fee steps already handed over are not, which is why the default is not taken until the operator side can be checked.

### Added

- **`agent.getTransfers(limit, offset, createdAfter | createdBefore)`** passes the SDK's time window through (one bound, a `Date`), and `spark-invoices.md` says how to match a payment to its invoice: `transfer.sparkInvoice`, present on the payer's and the receiver's records. The operators' clock can run seconds behind yours, so leave a margin when filtering by time.
- **The full eval set, run together for the first time: all 45 plus eight new ones (53–60).** Run with a different model, with-skill, on paper. No money-path regression; the misses are reply shape, and stale assertions in evals 2, 5, 23, 33 and 59 are corrected (`evals/NOTES.md`, `evals/findings-2026-10-27.md`).
- **`createTrackedInvoice(amountSats, memo)` and `getInvoiceStatus(id)`: one invoice per order that the shop can check.** `createLightningInvoice` returns only the BOLT11, and its default Spark fallback lets a Spark wallet pay with a plain transfer: on hosted REGTEST the money arrived and the invoice stayed `INVOICE_CREATED`. A tracked invoice needs an amount and has no fallback, so every payer pays over Lightning. `getInvoiceStatus(id)` reads the SSP's status as a `state` a shop can act on (`unpaid`, `in_progress`, `received`, `paid`, `failed`, `failed_after_payment`, `unknown`), with `customerCharged`, `expired` and `canReinvoice`, which turns true only two minutes after expiry while unpaid or failed: an early failure may not be final, and re-invoicing sooner could charge a customer twice. The states are inferred from the SSP's schema and the operators' preimage swap in the Spark repo; SDK 0.14 reports the SSP's newer statuses (`HTLC_RECEIVED`, `HTLC_FAILED`, …) as `FUTURE_VALUE`, read as `unknown`. Funded REGTEST tests pin a payment on defaults, an expired invoice, a shop wallet closed while it was paid, and the untrackable fallback invoice.
- **`getTokenTransactions({ tokenIdentifier, limit })` and `getTokenTransaction(hash)`**, where to look after a token send threw `PAYMENT_COMMITTED`: `getTransfers()` lists sats only, and SKILL.md's rule now says so. Entries come back newest first (the operators page oldest-first, so a plain query returned the wallet's oldest transactions) and readable: hex `hash`, `status` (`finalized`, `pending`, `cancelled`), `type`, and each output's recipient address and key (compare by key: one key has a legacy `sp1…` and a `spark1…` address), whether it is this wallet's, token and amount. The order relies on undocumented operator behavior (no cursor plus `direction: "PREVIOUS"` returns the newest page); the funded test fails if that changes. A send's hash, as `transferTokens` returns it, finds it directly. Pinned by a funded REGTEST test with real token sends.
- **`batchTransferTokens(transfers, { dryRun })`**, with a preview that lists each entry and each token's total.
- **Withdrawals to BIP-352 silent payment addresses, documented and tested** (spark-sdk 0.14). `SparkAgent.withdraw({ to: "sp1q…" })` already passed the address straight to the SDK, which now accepts version 0 silent payment addresses (`sp1q…` mainnet, `tsp1q…` testnet/signet, `sprt1q…` regtest) and verifies the SSP's proof before signing. `wallet.md` → Silent payment addresses covers the call, why an explorer search for the address finds nothing (hand over the txid), the `sp1q…` vs legacy `sp1p…` Spark-address prefix, exact-match allowlist entries, and the two SDK calls that refuse them. New funded REGTEST test (`silent-payment-withdraw.test.js`): a withdrawal through `SparkAgent` to an address built from our own keys, scanned on the explorer by an independent BIP-352 receiver (`tests/helpers/silent-payment.js`, pinned to the BIP's own vectors in `tests/unit/silent-payment-helper.test.js`). It finds output 0 carrying exactly `amount − quoted fee` under those keys and no others. It also checks that a mainnet address is refused on REGTEST, that the default 10% fee ceiling still applies, and that a Spark transfer to one is refused, all before anything moves.

- **What the skill can and can't do on L1, written down** (`references/wallet.md` → On L1, with a rule in SKILL.md and pointers in `architecture.md` and the README). It is a Spark wallet, not an L1 wallet. On-chain it sees only its own Spark deposit addresses, through the operators, who answer only for addresses they issued (an arbitrary address returns an error, checked on REGTEST). It can't read any other address, including ones another wallet derives from the same mnemonic (Spark's keys sit at `m/8797555'/…`), and it can't spend L1 coins outside Spark. The section lists every L1 operation the SDK offers, wrapped or raw: deposit addresses, deposit status, claims (including the untested instant claim), static-deposit refunds, withdrawals, the SSP's withdrawal record, unilateral exit, watchtower-leaf recovery and `broadcastTx`. It also lists every call where the SDK queries its block explorer itself (one Esplora server, `mempool.space` on MAINNET unless `electrsUrl` is set, which two standalone helpers ignore). That includes the deprecated `getLatestDepositTxId`: it takes any address, and it returns `null` on a server error too, so a `null` doesn't mean nothing arrived (both checked on REGTEST). And it says what the agent should tell a user whose coins went to another address. SKILL.md also notes that `listPendingDeposits()` covers the static address and any unclaimed single-use ones. New user-story eval 50.

- **What to do instead of an address per order, and what to tell someone whose coins are stuck** (`references/wallet.md`, with a line in SKILL.md). One static address serves the wallet; to tell payers apart, give each order its own `createTrackedInvoice` (below). A txid an on-chain customer sends proves nothing: the address is shared and its transactions are public. Coins already at a single-use address arrived and wait on the operators: back up the recovery words, and follow buildonspark/spark#165. Evals 51 and 52 cover both.

- **Which payment hash each merchant gives you.** `bitrefill.md` now says the checkout returns none (pass `expectedPaymentHash: null`), and its payment step points only at `payMerchantCheckout`; `nadanada.md` says to bind to `data.paymentHash`. An eval agent had guessed the Bitrefill answer.
- **Don't put the agent's recovery words into another wallet app** (`references/security.md`). That app gets the same full control, the addresses it shows are invisible to the agent, and a Spark app opens the wallet with its own fee-ladder setting. `reveal-mnemonic` says so on screen. Both eval-50 runs raised the shared-seed risk unprompted.
- **A silent-payment withdrawal's txid isn't proof of who was paid** (`references/wallet.md`), and `verifyVault()` is read by its `ok` (`references/unilateral-exit.md`).

### Fixed

- **`encrypted-seed.md` no longer suggests `reset-ledger` to make a budget take effect.** The running-agent warning applied only to an agent with an `.env` budget, and nothing said `set-policy` creates or signs the ledger itself, so an eval answer told a user to run `reset-ledger`, which empties the spend window, as a binding step. The two cases are separate now; without an `.env` budget a running agent keeps no ledger and simply spends unbudgeted until restarted.
- **`claimDeposit` checks the static address first.** A failing single-use address query used to fail static claims too, and a server that ignored the paging offset kept the lookup going forever; it now stops at a repeated page or after 10,000 UTXOs with `DEPOSIT_LOOKUP_INCOMPLETE` ("can't tell"), not "not found".
- **The samples load `.env` again.** Since importing `sparkbtcbot-skill/agent` stopped loading it, the code `setup` prints and the Usage samples in `l402.md` and `agent-class.md` failed with `NO_PASSPHRASE` for anyone keeping the passphrase in `.env`. Each now starts with `import "dotenv/config"`.
- **`set-policy` says to stop the agent first.** An agent started before the first bind keeps the old policy and rewrites the new signed ledger unsigned on its next spend, which the bound boot then refuses. The confirmation prompt and `encrypted-seed.md` say so; a code guard is still to come.
- **Stale lines:** `lightning.md` said any `…_FAILED` status resets the dedup id, `merchant-spending.md` that `payAndSettle` throws only on terminal failure (a final failure now has code `LIGHTNING_PAYMENT_FAILED`), `first-spend.md` gave the wrong default ceiling for `payMerchantCheckout`, and the reveal command in `wallet.md` worked only in a cloned repo.
- **`fetchL402` is tested end to end on REGTEST** against a local L402 server issuing real invoices: a purchase, delivery failing in transit then recovered, a refused pass and `forgetL402`, a POST re-sent only with `resend`, a dying token, an expired invoice, the budget counting each purchase once, and the shop's view (`tests/integration/funded/l402-local-server.test.js`, needs openssl).
- **Single-use deposit addresses are refused.** The operators currently refuse the step that claims them (`finalize_deposit_tree_creation` UNAVAILABLE on MAINNET and REGTEST, 2026-10-26; a real 2,000-sat mainnet deposit was refused), and the SDK has no refund path for them. `getSingleUseDepositAddress()` throws `SINGLE_USE_DEPOSITS_UNAVAILABLE`; `listPendingDeposits()` still lists single-use deposits, typed, so coins already sent show as arrived-but-waiting; `claimDeposit` asks the operators where the deposit sits and claims only one at the static address: the SSP quotes a single-use deposit as if it would claim it (a 1,703-sat credit on the stuck 2,000), so a dry run would have promised money the claim then refused. A single-use deposit is refused with the reason and a reminder to keep the recovery words backed up, and one it can't find is refused with `DEPOSIT_NOT_FOUND`, both before any quote (checked against the stuck mainnet deposit). Docs and the example script hand out only the static address, and the example lists coins already sent to a single-use address instead of saying none arrived.
- **The example script's claim hint named the wrong call.** `balance-and-deposits.js` printed `claimStaticDeposit({ transactionId, outputIndex, maxFee })`; that function takes a quote's `creditAmountSats` and `sspSignature`, not a `maxFee`, so the copied line failed. It now prints `claimStaticDepositWithMaxFee`.
- **`payAndSettle` no longer calls a paid payment "failed".** `PREIMAGE_PROVIDING_FAILED` and `TRANSFER_FAILED` come after the Lightning payment succeeded, but an `_FAILED` suffix match treated them as nothing-paid and forgot the dedup id. They now throw `PAYMENT_COMMITTED` at once; only the payee-unpaid statuses are terminal, and an unknown status keeps waiting. An invoice with more than one payment hash is refused before paying, since no preimage can be checked against it.
- **`fulfillInvoice` hands the SDK checked amounts and never calls a mixed batch "nothing sent".** Token amounts go out as bigint base units (a string `"100"` used to be read as hex, 256 units) and only for amountless invoices; a tokens-plus-sats batch whose SDK call throws is always `PAYMENT_COMMITTED`, because the SDK sends the tokens before it can fail the sats leg with a "pre-send" message; failed token transactions now name their invoices.
- **`withdraw`'s missing-record error is a `PaymentCommittedError`**, like every other money-may-have-left case, and SKILL.md has the rule: on `PAYMENT_COMMITTED` never pay again with a new invoice, address or method.
- **Smaller review fixes:** a `transferTokens` dry run refuses a Spark invoice, as the send does; a batch entry naming two different recipients is refused; `first-spend.md` pays merchants through `payMerchantCheckout` (Lightning only); the shell-safe id pattern no longer admits a leading `-` or `..`; `l402.md`'s caching wrapper keys by https origin and keeps a recovered pass; SKILL.md's sample follows its own one-shot rule and no longer implies token sends are capped; the setup test that creates a REGTEST wallet moved from the unit tier to integration, and `setup` asks for the passphrase before it generates a wallet, so a missing one fails before any network call and the unit tier no longer reaches REGTEST.
- **Lightning payments report what they cost: `feeSats`.** `payLightningInvoice` and `payAndSettle` passed on the SDK's first answer, whose `fee` can read 0. On hosted REGTEST (2026-10-02) that answer came back `TRANSFER_COMPLETED` with the preimage and a fee of 0 msat; the next status read said 5,000 msat, and 1,005 sats had left for a 1,000-sat invoice. A paid result now carries `feeSats`, in whole sats, from status reads once the payment has settled (up to 5, 2 s apart, or `payAndSettle`'s `pollMs`): the larger of the fee the SSP reports and what the transfer took beyond the amount. A 0 counts only when the transfer confirms it. While the cost isn't known (not settled, or still unpriced), `feeSats` is the fee cap and `feeNote` says why. A payment over Spark reports 0. `fetchL402` skips the reads: its paid pass is waiting to be presented. The result is now a copy, so `dedupReused` can't be lost on a frozen SDK object. Ported from the parked `sdk-013` line.
- **`set-policy` no longer empties the spend window when a budget changes.** It wrote a fresh, empty signed ledger on every budget change, so tightening a limit freed headroom: lower a 50,000-sat budget to 20,000 after 30,000 was spent, and the agent could spend 20,000 more that day instead of nothing. Now a ledger that verifies is kept and spends already in the window count against the new budget; a missing ledger is created; an unsigned env-budget ledger is signed as it stands. A ledger that fails verification or can't be read stops the ceremony with nothing changed. Only `reset-ledger` empties the window on purpose. Checked through the real TTY ceremony: with 49,000 spent, binding 50,000 and then tightening to 20,000 kept 49,000 counted both times. Ported from the parked `sdk-013` line, without its token budgets.
- **`setup` on a pipe no longer succeeds silently or hangs.** With stdin at EOF and no `SPARK_PASSPHRASE`, the passphrase prompt was left pending and Node exited **0 with nothing written**; an open-but-silent pipe hung until something killed it. The shared prompt helper now rejects on EOF (`PROMPT_EOF`) and after `SPARK_PROMPT_TIMEOUT_MS` of silence (default 30 s, `PROMPT_TIMEOUT`), so setup exits 1 with the reason and the fix. Piped input — the CI path — is unchanged. Ported from the parked `sdk-013` line.
- **`SparkAgent` is importable from the package: `import { SparkAgent } from "sparkbtcbot-skill/agent"`.** The exports map blocked the deep path, so on the npm route the only way to the wrapper was to copy an 1,100-line listing. A field test on real mainnet found the cost: a mid-tier model built every script on the raw `SparkWallet`, so no guard ran on a live send. SKILL.md's first code sample now uses `SparkAgent` (the raw one is a single line for library authors, still with `sparkWalletOptions`), and the one-shot rule covers read-only scripts too, because boot claims pending transfers and that can start the leaf optimizer. A new test packs the real tarball into a scratch project and imports, by package name, every specifier and symbol any shipped doc tells an agent to write. Ported from the parked `sdk-013` line.
- **`l402.md`'s snippets run as written.** The Usage Example called `SparkAgent` without importing it, loaded the seed from a clone-only path and left `cleanup()` unawaited. ## 0.6.2 — 2026-08-20

> **Note:** 0.6.3 corrects one line below. `npm ci` runs install scripts, so it needs `--ignore-scripts` too — the bare `npm ci` recommended here does not protect you.

### Security

- **An npx rule that holds without a prompt.** Since 0.5.0 the mitigation against npx's registry fallback had been "if npx offers to install something, answer NO and stop," carried in SKILL.md, AGENTS.md and README. That rule assumes a prompt. Verified against npm 11: **npx only prompts on an interactive TTY.** With no TTY — a CI job, a script, or an AI agent running commands through a tool call, which is the context SKILL.md and AGENTS.md exist for — npx installs the fetched package and executes it silently, with nothing displayed and nothing to decline. The flag costs nothing: the CLI resolves and runs, and both `sparkbtcbot-skill` and `@buildonspark/spark-sdk` import cleanly without install scripts.

- **`cli.js` argument gate no longer falls through on inherited `Object` properties.** The dispatcher looked up `COMMANDS[cmd]`, which walks the prototype chain, so `sparkbtcbot constructor`, `toString`, `valueOf` and `__proto__` resolved to a truthy non-entry and reached `import(undefined)` — a stack trace instead of the usage message, in the one gate whose own comment promises that an unknown command "cannot fall through to anything." Now `Object.hasOwn(COMMANDS, cmd)`. Not exploitable (nothing executed, exit stayed non-zero), but it was the 0.4.3 fall-through class in miniature.

### Security

- **One CLI, and its name is ours: the five per-command bins collapse into a single `sparkbtcbot <command>` dispatcher.** The 0.4.x–0.5.x bins (`sparkbtcbot-setup`, `sparkbtcbot-reveal-mnemonic`, `sparkbtcbot-leaf-vault`, `sparkbtcbot-set-policy`, `sparkbtcbot-reset-ledger`) were five *unregistered* npm names — each a separate landing spot for npx's registry fallback when the local bin is missing, at wallet-bootstrap or seed-reveal time. The dispatcher also gives the ceremonies **one argument gate with no default action** (the 0.4.3 `--help`-minted-a-wallet class of bug cannot recur per-script), `sparkbtcbot` with no arguments prints the subcommand list instead of hitting the registry with a half-remembered name, and every command module is now **inert on import** with an exported `main()` — `set-policy`, `reset-ledger`, and `leaf-vault` previously executed at top level on import. Old invocations migrate mechanically: `npm exec --no -- sparkbtcbot-setup` → `npm exec --no -- sparkbtcbot setup`. The `npm run` script names in the cloned repo are unchanged. **Breaking:** the five old bin names are gone; docs-lint fails any living doc that resurrects one.

### Changed

- Docs, in-code error messages (`spend-ledger`, `spark-agent`), evals, and tests all speak the `sparkbtcbot <command>` form; README/SKILL.md/AGENTS.md npx guidance updated for the owned-name fallback.

## 0.5.0 — 2026-08-17

### Security

- **Trail-of-Bits pass on the seed-binding work — 8 findings fixed before release.** Two independent adversarial reviews (crypto/format + install/docs/reveal) ran against this batch; the crypto core survived every malleability and payload-edge-case attack, but the *rollout* had holes: (1) `references/agent-class.md` — the "drop-in" class users actually copy — still shipped the pre-seal env-only resolver, so someone who sealed a budget and followed the doc got **no budget at all**; (2) a sealed seed whose policy didn't reach the agent ran **silently unbound** — now the plaintext version byte is checked and a sealed-but-unbound wallet **throws**; the context also moved to `globalThis` (duplicate module copies) and a policy-less load can no longer clear an established one; (3) the seed header wasn't in the GCM AAD, so flipping `0x02`→`0x01` passed authentication and reinterpreted the payload as a bare mnemonic — v2 now authenticates the header (v1 untouched); (4) `npx <cmd>` does **not** fail closed — it fetches a registry package *named after the command*, and all five of our bin names were unregistered; docs now use `npm exec --no`, and both agent-facing rule files say to refuse any npx install offer; (5) the ceremonies read the passphrase from `.env` (which sits next to the wallet), reducing "requires the passphrase" to "requires a PTY" — they now always prompt; (6) the over-budget error told sealed-policy callers to edit `.env`, the exact move the seal neutralizes; (7) `SIGTERM`/`SIGHUP` skipped the seed-reveal screen wipe (the `exit` hook doesn't run for signals), leaving the mnemonic on screen indefinitely; (8) the reveal claimed "alternate buffer wiped" unconditionally, but GNU screen ships `altscreen off` — the message is now conditional and tells screen users to clear their scrollback. Also: README no longer teaches an unpinned SDK install, the pin-staleness tradeoff is stated, and `npm@latest` on Node 20 is corrected (engines are warn-only, so it installs npm 12 anyway — use `npm@11`). +12 regression tests.

- **Seed-bound spending policy (opt-in): the budget can now be sealed inside the encrypted seed.** Guard enforcement used to depend on files the agent can write — `rm ~/.spark/spend-ledger.json` (or truncating it, or editing `.env` to drop `SPARK_DAILY_BUDGET_SATS`) silently restored the full budget; a cleanup command, a prompt injection, or a machine migration all failed open. Now `npx sparkbtcbot-set-policy` (user-run, TTY-gated) binds `dailyBudgetSats` into the encrypted seed payload (**v2 seed format** — reading it needs the passphrase, tampering fails the GCM tag, deleting it deletes the wallet: the agent can't remove the budget without removing the money), and the spend ledger becomes **HMAC-signed** with a seed-derived HKDF key (never the AES key). Under a bound policy, a missing / unsigned / edited ledger **fails closed** with instructions to run `npx sparkbtcbot-reset-ledger` — the passphrase-gated legitimate reset that finally makes reset distinguishable from attack (previously `rm` was both). A seed-bound budget wins over the env var absolutely. **v1 seeds and env-var budgets are completely unchanged** — no policy, no new behavior. Honest limits, documented: the bar moves from `rm` to *executing code*, not to impossibility; replay of a validly-signed old ledger is undefendable client-side; raw-SDK calls still bypass wrapper guards. New exports: `loadSeedPayload(FromEnv)`, `validateSeedPolicy`, `deriveLedgerHmacKey`, `initSignedLedger`; new CLIs: `sparkbtcbot-set-policy`, `sparkbtcbot-reset-ledger`. 16 attack-first tests (each attack proven to throw).

### Changed

- **Agents are explicitly told that running SETUP is allowed and expected.** Live testing showed agents over-extending the reveal-mnemonic prohibition into refusing `npm run setup` when the user asked — citing rules the docs never contained (setup has not printed or written the mnemonic in plaintext since 0.4.0). AGENTS.md and SKILL.md now carry an affirmative rule: creating the wallet on the user's behalf is the designed flow; the only secret to guard during setup is the passphrase, which goes to `.env` and is never echoed.

### Security

- **`--help` no longer performs the CLI's default action.** All three published CLIs ignored unrecognized arguments and fell through to their default — which for `sparkbtcbot-setup` is *creating a wallet*: an agent probing `--help` for usage silently bootstrapped a real, unbacked wallet (caught by QA on REGTEST before it happened on MAINNET). `sparkbtcbot-leaf-vault --help` would likewise have taken a snapshot, and a typo'd flag to `sparkbtcbot-reveal-mnemonic` fell through toward a seed reveal. ## 0.4.0 — 2026-08-05

First npm release since 0.3.0 (0.3.1 shipped only to the plugin marketplace), folding in the full 0.4.0 line. The sections below run newest-first; the entries following the second group of headings are the earlier 0.4.0-line work from July.

### Fixed

- **BigInt sats amounts no longer bounce off the SDK.** The SDK validates every amount with `Number.isSafeInteger()`, which is `false` for *all* BigInts — so `transfer({ amount: 8258n })` threw a misleading `"Sats amount must be less than 2^53"` while `8258` worked, and since `getBalance()` returns balances *as* bigint, passing one straight back in was the natural mistake. A `toSats()` normalizer (number|bigint → safe-integer Number, clear pre-I/O error on garbage) now guards every SDK-bound sats amount across `transfer`, `withdraw`, `createLightningInvoice`, `createSatsInvoice`, `payLightningInvoice`, `estimateLightningFee`, and `getWithdrawalFeeQuote` — and `transfer`'s dry-run and live paths now validate identically instead of diverging. Token amounts are deliberately untouched (legitimately bigint on the LRC20 path).
- **L402 challenges are read from the `WWW-Authenticate` header, and the `token=` field parses.** `fetchL402`/`previewL402` called `response.json()` unconditionally on a 402 and never read the header — the spec-standard location — so a header-only server (aperture, lightningfaucet) threw `Invalid L402 challenge`. And every parser matched only `macaroon="..."`, structurally unable to match the current spec's `L402 version="0", token="..."` form. One shared `parseL402Challenge()` (exported) now reads the header first, falls back to the body, and extracts each field by name — any scheme prefix (L402/LSAT), any field order, `macaroon=` or `token=` — applied consistently to the wrapper, the example script, and the reference docs that had drifted apart.
- **The leaf-vault no longer cries BROKEN during every cooperative L1 exit.** An exit removes its leaves from `getLeaves()` at broadcast while `owned` keeps counting the exiting sats until the L1 tx confirms — minutes during which every snapshot read as a partial capture and marched the BROKEN marker up. Balances alone can't distinguish that window from a genuinely dropped transfer-locked leaf (identical signature), so the fix demands *positive evidence*: the shortfall is excused only when the capture still covers `available`, the gate-proven UNION bundle was written (in-flight leaves keep their exit material), *and* the SSP confirms a pending `COOP_EXIT` via `wallet.getUserRequests` — with absence/failure/zero degrading to the old strict behavior, so the guard is never weaker than before. Full-balance exits still trip the (deliberately untouched) empty-capture guard.
- **One-shot scripts that move value no longer race the SDK's background leaf optimizer.** Value-moving ops fire `autoOptimizeIfNeeded()` detached; `cleanup()` right after tore down gRPC mid-optimization and logged the alarming (but harmless) `Claim transfer process was interrupted due to cleanup`. `SparkAgent.create(..., { optimizeLeaves: false })` now plumbs `optimizationOptions.auto` so a one-shot has nothing to interrupt; documented in `wallet.md`/SKILL.md, and the L402 example (the one shipped script that pays then exits) uses it.

### Changed

- **Node floor raised to `>=20`; CI now audits dependencies.** `engines: >=18` was a claim CI never tested (matrix is 20/22/24) for a runtime that hit EOL in April 2025. A separate CI `audit` job runs `npm audit --audit-level=high` (postcss and protobufjs advisories were cleared to a 0-vulnerability tree). npm supply-chain guidance is now tiered and explicitly **not a gate**: prefer npm 12+ (install scripts disabled by default; needs Node 22.22.2+/24.15.0+), accept 11.10.0+ (the `min-release-age` floor — fine on Node 20), and proceed with a warning on older — never block wallet setup over the npm version.
- **Merchant references re-verified live (2026-08-05).** nadanada: the VPN purchase endpoint moved (`/vpn/purchase` → `/vpn/request`; the old path 404s), all responses are wrapped in `{ success, data }`, the full request body is documented including that the WireGuard keys go in the *purchase* body, the returned config's empty `PrivateKey =` must be injected locally, and a key-generation snippet covers Node's X25519 export quirk. Cryptorefills: the granular MCP catalog tools work again (the earlier 400s were a missing `brand_name` argument), documented with their field shapes — which differ from the x402 REST catalog's — while the wizard remains the only checkout verified end-to-end. README now names the two live-validated stacks: Claude Code, and opencode running GLM-5.2 via OpenRouter.
- **Boltz dependency removed; the native Lightning↔L1 bridge is documented in both directions** (ported from the 0.3.1 release, prompted by Boltz disabling all swaps indefinitely in August 2026). New `references/lightning.md` sections for the Lightning → L1 off-ramp and L1 → Lightning on-ramp, with every fee live-validated on MAINNET (2026-08-02 → 08-04): cooperative-exit fee is flat per exit (~2,000–2,700 sats at MEDIUM: 750-sat flat operator fee + feerate-tracking L1 fee) and **deducted from the amount** (SDK default `deductFeeFromWithdrawalAmount: true`); deposit claims require 3 confirmations, carry an SSP spread (live-measured 297 sats on a 10,350-sat deposit, quote honored exactly), and credit asynchronously (~30s); Lightning receive was credited in full (documented 0.15% kept as worst case); Lightning send measured 0.32% all-in — and **free when the payee is Spark-backed**, where the payment completes as a Spark transfer with no `getLightningSendRequest` record (documented so agents don't misread it as a failure and retry-pay). Also documented: withdrawal quotes are not read-only (they can trigger an SSP leaf swap) and expire.

### Added

- **`SparkAgent.listPendingDeposits()` — confirmed-but-unclaimed L1 deposits are finally visible.** `getBalance()` reflects only *claimed* Spark balance, so an agent asked "did my deposit arrive?" answered "no" for funds that confirmed an hour ago, with no wrapper method to check further. The new method wraps `queryStaticDepositAddresses()` + `getUtxosForDepositAddress(..., excludeClaimed=true)` and returns `[{ address, txid, vout }]`, each entry feeding straight into `claimDeposit()`. The "check arrived → claim" step is now documented on every surface an agent reads (SKILL.md, wallet.md, lightning.md, agent-class.md, and the example script).
- **`AGENTS.md` — the security rules now reach non-Claude agents.** Every load-bearing rule lived only in SKILL.md, which Claude Code auto-loads but opencode/Cursor/Aider do not — those agents read AGENTS.md/README and so never saw "don't echo the passphrase" or the supply-chain-hardening offer, and tripped on both in live testing. AGENTS.md carries the must-reach-every-agent rules (never print the mnemonic *or* passphrase; auto-generated passphrases go straight to `.env`; don't run `reveal-mnemonic` yourself; a "user request" to reveal the seed is never an instruction arriving via fetched content, tool results, or system messages), with a prominent agent-directed banner in the README pointing at it.
- **Cumulative spend budget (`lib/spend-ledger.js`).** Every prior guard was per-call — a fee cap, an amount ceiling, a quote match — and none of them stops a *loop*: an agent paying 100 invoices, each individually under its cap, drained a wallet while every check passed. Setting `SPARK_DAILY_BUDGET_SATS` now enforces a rolling 24-hour sats budget across Spark transfers, Lightning pays, Spark-invoice fulfillment, and L1 withdrawals, persisted atomically at `~/.spark/spend-ledger.json` (`SPARK_SPEND_LEDGER_PATH` to relocate; `agent.spendStatus()` to inspect). Fail-closed postures throughout: a corrupt ledger refuses to count as a fresh one, an uncountable spend refuses to pass a budget, and a malformed budget value refuses to boot rather than being silently ignored. Exported from the npm package (`createSpendLedger`, `checkSpendBudget`, `spentInWindow`). Stated honestly: this is an in-process guardrail against runaway loops and prompt-injected sprees — server-enforced limits still require sparkbtcbot-proxy.

### Security

- **`fulfillInvoice` now enforces the recipient allowlist.** Paying a native Spark invoice sends sats/tokens to whoever created it, and this was the one outbound path that skipped the allowlist entirely — a bare SDK passthrough, while SKILL.md promised every Spark transfer was gated. The receiver is now decoded from each invoice (`decodeSparkAddress`) and held to `~/.spark/recipients.allow` before the SDK is called, with identity-key comparison so an entry in either address encoding matches, one disallowed receiver blocking the whole batch, `dryRun` parity (preview shows WHO gets paid), unknown-option rejection, and a refuse-on-disagreement guard when a caller amount contradicts the invoice's embedded amount.
- **`SparkAgent.create()` refuses a missing mnemonic instead of minting a wallet.** The SDK generates a fresh wallet for an undefined `mnemonicOrSeed`, so a typo'd env var or failed seed decrypt silently booted a brand-new MAINNET wallet — and deposits landed on a wallet whose seed nobody backed up. Deliberate creation remains `npm run setup`.
- **Ported from the 0.3.1 adversarial review:** `getReference()` rejects path-traversal names (`^[a-z0-9-]+$` — a crafted name could read arbitrary `.md` files outside the package; regression test included); all six example scripts now run their demo only when executed directly, never on import; `SparkAgent.withdraw` binds the exit via the non-deprecated `feeQuoteId` + `feeAmountSats` (the `feeQuote` object param is `@deprecated` in current SDKs).
- **Guard VALUES are validated, not just guard keys.** The misspelled-option doctrine covered names but not values: `claimDeposit({ maxFeePct: "10%" })` produced a `NaN` ceiling that the SDK's `feeCharged > maxFee` check never trips (NaN comparisons are false) — the claim proceeded at any spread; `withdraw` garbage degraded to an `Infinity` cap ("no cap set"); `payLightningInvoice`/`fetchL402` ceilings degraded the same way. Every numeric guard option now throws on an unreadable value before any I/O (`requireNumericOption`) — absent is a choice, garbage is a bug. Also: `batchTransferTokens` entries with no readable receiver now fail closed (previously the allowlist gate was silently skipped for them).
- **Misspelled guard options now throw instead of meaning "no cap".** `checkL402Amount({ maxAmountSat: 500 })` used to return ok — the keystroke that feels like setting a ceiling silently removed it. All option-taking guards in `lib/fee-guards.js` reject unknown keys, matching the wrapper's existing strictness.
- **`claimDeposit`'s fee ceiling is size-aware.** The flat 5,000-sat default authorized the SSP to take 83% of a 6,000-sat deposit. The default is now `maxFeePct` (10%) of the quoted credit — the same posture as `withdraw` — with explicit `maxFeeSats` still winning and an unreadable quote failing closed.
- **`estimateFirstFeeCap`'s estimate-driven growth is bounded.** The live estimate could raise its own cap without limit, so an inflated estimate from a hostile counterparty grew the cap instead of tripping it. Growth is now capped at 3× the amount-scaled cap (override with `maxCapSats`).
- **`l402-paywalls.js` uses the library fee cap.** The example script inlined `max(10, 0.5%)` — re-inheriting the exact under-cap failure (`floor 25`) already fixed in `lib/fee-guards.js` for anyone who copy-pasted it.

### Added

- **Unilateral-exit backup — the "leaf vault."** A Spark seed alone **cannot** unilaterally exit to L1: exit needs the tree of pre-signed node/refund txs ("leaf material") that operators hand the wallet at claim/transfer time, and that material is **not** derivable from the seed. This release adds the backup half; the exit itself is performed by Blink's production tool (below):
  - `lib/leaf-vault.js` + `skills/sparkbtcbot/scripts/leaf-vault.js` — continuously mirror the leaf material to `~/.spark/leaf-vault/current.json` in **`spark.unilateral-exit-bundle.v1`**, the exact bundle format consumed by [blinkbitcoin/spark-unilateral-exit](https://github.com/blinkbitcoin/spark-unilateral-exit)'s CLI. Each node is stored as its **canonical `TreeNode` protobuf hex** (the SDK's exact wire bytes), so recovery is a byte-faithful decode, not a fragile field-by-field JSON reconstruction. `enableLeafVault(wallet)` snapshots on boot, on every `balance:update`, and on a safety-net timer; a **fail-loud self-check** throws if the reached-into SDK internals move; an **integrity gate** refuses to write a vault unless it provably reconstructs every leaf's exit chain **offline** (no operators). `verifyVault()` / `npm run leaf-vault -- verify` re-checks any vault (exit codes: 0 ok, 1 broken/critical, 2 indeterminate).
  - **Recovery is performed by Blink's tool, not a bundled one.** The operatorless exit is done by [blinkbitcoin/spark-unilateral-exit](https://github.com/blinkbitcoin/spark-unilateral-exit) — tested on real mainnet, with per-leaf economic triage (skips uneconomical dust) and TRUC confirm-and-continue plus the CPFP fee-bumping and ~2,000-block CSV timelock. Point it at the leaf-vault's bundle plus an L1 fee UTXO you control; see `references/unilateral-exit.md`. (An earlier hand-rolled `scripts/unilateral-exit.js` was dropped as naive by comparison.)
- **Fee guardrails on every value-moving path** (`lib/fee-guards.js`). Bounds both the fee **and** the amount on Lightning sends, L402 payments, deposit claims, and withdrawals, so a tampered SSP quote or an amountless invoice can't move more than the caller allowed. Wired into `SparkAgent`: `payLightningInvoice` takes `maxFeeSats` + `maxAmountSats`; deposit claims use the SDK's `claimStaticDepositWithMaxFee`; L402 enforces an amount ceiling.
- Explicit runtime dep `@noble/curves`, plus the `npm run leaf-vault` script.

### Changed

- **Corrected overstated backup/exit claims** in `SKILL.md` and `references/architecture.md`. "The mnemonic is the entire backup" and "Spark guarantees you can always exit to L1" are now accurate: the seed recovers the wallet **while operators are online**, but **unilateral exit additionally requires the locally-backed-up leaf material**. Normal recovery is unchanged — the correction is specifically the operators-gone case.

### Security

- **leaf-vault: refuse to publish a partial capture over a complete bundle.** `getLeaves` can transiently return a non-empty *subset* of the wallet's leaves (its coordinator recover path swallows failures), and each present leaf still passes the integrity gate — so an unchecked partial snapshot would atomically overwrite a complete bundle, health still green, silently stranding the dropped leaves' only backup. The snapshot now keeps the prior complete bundle (and surfaces the failure) unless a matching balance decrease confirms the dropped leaves were genuinely spent. Generalizes the existing empty-`getLeaves` guard to the partial case.
- **Withdrawal fee ceiling now binds the executed exit.** `withdraw` checked a fetched quote against a ceiling but then executed the exit without passing a fee, so a re-priced or unreadable quote bypassed the ceiling. It now passes the vetted `feeQuote` into the SDK (which derives `feeAmountSats` + `feeQuoteId`), so the operator charges the fee that was checked, and fails **closed** when the quote fee is unreadable instead of deferring to an SDK cap that does not exist for this path.
- **leaf-vault guards now judge OWNED sats, not available.** The balance probe read the SDK's top-level `balance` first — a deprecated alias for **available** — so the shrink/empty guards and the CLI's severity judgment silently excluded funds locked in in-flight transfers/swaps: a snapshot during a lock window could overwrite the prior bundle and drop a still-owned leaf's only exit material. The probe now prefers `satsBalance.owned`, stated in one `ownedSats()` helper, and the test mocks use the real SDK response shape so the ordering is pinned.
- **Network label is derived through the proto codec and gated.** With no `networkLabel` (the documented raw-SDK path), the fallback stringified the leaf's **numeric** proto enum — persisting `network: "1"`, which verifies green locally but is refused by Blink's recovery CLI, and mis-mapping the online ancestor query via the utils enum's reverse mapping. The label now goes through `networkToJSON`, and a bundle whose network is not one Blink accepts (`MAINNET/REGTEST/TESTNET/SIGNET/LOCAL`) is refused loudly instead of written.
- **A different wallet or network can no longer clobber the shared default vault.** The snapshot now refuses to overwrite a prior bundle whose `network` or `walletIdentityPublicKey` doesn't match the capturing wallet (e.g. a REGTEST run on a machine whose bundle protects a mainnet wallet) — set `SPARK_LEAF_VAULT_PATH` per wallet instead.
- **Blocked shrink guards now rescue fresh leaves (union bundle).** When the shrink guard blocks a partial capture, leaves present only in the fresh capture (a new deposit, a claimed transfer) previously had no persisted exit material for as long as the guard tripped. The snapshot now writes a union bundle (fresh capture + provable carried-over prior leaves) when it passes the same offline proof, then still fails loudly.
- **Chronic empty captures now surface.** A persistently-empty `getLeaves` on a funded wallet was accounted as success — failure counter reset, `BROKEN` marker removed, health green — while the bundle staled. Skips no longer count as success; consecutive transient-empty skips trip the `BROKEN` marker, and the marker is cleared only by a genuinely persisted bundle (or a confirmed-empty wallet).
- **Setup prompts no longer echo the passphrase.** The interactive prompt never disabled terminal echo, so the passphrase appeared on screen and in any pty recording (tmux/asciinema/`script`); it now uses raw mode on a TTY. Piped input (`printf 'pass\npass\n' | npm run setup`) previously hung on the confirm prompt because the remainder of a stdin chunk was dropped; both prompt paths now carry unconsumed input across prompts.
- **`seed.enc` publish is race-free and power-loss durable.** The exclusive create had a check-then-act (TOCTOU) window in which two concurrent setups could silently swap the seed file, and its writer skipped the parent-directory fsync the leaf-vault writer documents as load-bearing. All persistence now goes through one shared writer (`lib/atomic-file.js`) that publishes exclusively via kernel-atomic `link(2)` and fsyncs the parent directory.

- **Receive-artifact guidance: which of the five receive rails to hand out.** A bot asked for "a spark address for 1000 sats" produced a native Spark invoice — which is address-*shaped* (same `spark1…` bech32m prefix as a bare address, with an embedded signed payment request) but payable ONLY by Spark-SDK code via `fulfillSparkInvoice`; the user's Xverse wallet couldn't pay it. SKILL.md now carries a decision table: "invoice"-type asks default to a BOLT11 via `createLightningInvoice({ includeSparkAddress: true })` (payable by any Lightning wallet, free for Spark-wallet payers via the fallback; 1-hour expiry silently by default, overridable on request); "address"-type asks get the bare, non-expiring `getSparkAddress()`; native Spark invoices only for known SDK-agent payers; L1 for on-chain/large amounts — plus a one-line alternatives disclosure instead of interrogating the user. `spark-invoices.md` leads with the payability warning and its `fulfillSparkInvoice` example no longer shows a legacy `sp1…` string the SDK rejects. Three new evals (10–12) pin the trap phrases.
- **`fetchL402`/`previewL402` existed only in the reference doc.** `agent-class.md` and `l402.md` both documented them as `SparkAgent` methods, but the shipped class never had them (`TypeError: not a function` for anyone importing it — found by a deployed bot); the doc also advertised a `createSparkInvoice` that exists nowhere and silently omitted eight shipped methods. The L402 methods now ship on `SparkAgent` (ported from the reviewed reference implementation, amount-capped and routed through the guarded Lightning path), the doc's code listing is regenerated from the shipped file, and a new two-way parity test fails the suite if the doc's method surface and the shipped class ever diverge again.
- **`SparkAgent.payLightningInvoice` dropped the amount on amountless invoices.** It passed `amountSats` to the fee estimate but never forwarded it to the actual payment, so zero-amount invoices always failed at pay time with `"must specify amountSatsToSend"` (dry run green, real send broken — found by a deployed bot). It now forwards `amountSatsToSend` **only when the invoice is amountless**, matching the SDK's contract, which equally rejects the parameter for invoices that carry an amount. `references/lightning.md` now documents the `amountSats` (estimate) vs `amountSatsToSend` (pay) naming split.

- **Phantom `dryRun` on the raw SDK — incident-driven fix.** A deployed bot passed `dryRun: true` to raw `wallet.transfer()`; the SDK has no such option, JS silently dropped it, and the "preview" call **sent real sats** (both calls sent; funds reached the intended address). Three-layer fix: SKILL.md scopes `dryRun` to the `SparkAgent` wrapper and warns that raw `wallet.*` money calls silently ignore unknown keys AND bypass the allowlist/fee guards; `references/wallet.md`'s transfer section carries the same warning inline; and `SparkAgent`'s money-moving methods (`transfer`, `transferTokens`, `withdraw`, `claimDeposit`, `payLightningInvoice`) now **throw on unknown option keys**, so a mistyped flag fails loudly instead of silently spending. New skill eval (id 9) pins the behavior.

### Removed

- `loadEncryptedMnemonic` (unused alias of `loadMnemonic`) and the dead `operatorSet`/`appVersion` snapshot options.

### Added (hardening pass)

- npm subpath exports `sparkbtcbot/leaf-vault` (SDK reach-in API) and `sparkbtcbot/leaf-vault/core` (SDK-free validators) so npm-package consumers can actually attach the vault the docs describe.
- `judgeMissingVault()` — the CLI's 0/1/2 exit-code severity contract as a testable function; `vaultHealth()` now also reports `consecutiveTransientSkips`.
- 29 new unit tests: network derivation, identity guard, union rescue, skip accounting + `BROKEN` lifecycle (fatal vs threshold vs recovery), debounce coalescing, interval safety net, dispose/double-dispose races, the missed-event re-arm, `verifyVault`'s ENOENT contract, atomic-writer failure paths, exports-map resolution, and the SparkAgent enabled path.

## 0.3.0 — 2026-05-29

### Added

- **Opt-in outbound recipient allowlist** (`lib/recipients-allowlist.js`). When `~/.spark/recipients.allow` exists with at least one entry, transfers and cooperative withdrawals to any address not on the list fail; a missing or empty/all-comments file leaves the gate unenforced. Spark (`sp1…`) and L1 addresses share one file (one per line, `#` comments allowed), matched as plain strings. New exports `loadRecipientsAllowlist`, `assertRecipientAllowed`, `DEFAULT_ALLOWLIST_PATH`; enforced in `spark-agent.js` on transfer/withdraw (Lightning BOLT11 sends are not gated, since they target node pubkeys). This is an operator-surprise guardrail, **not** a defense against a compromised agent (which can rewrite the file) — `sparkbtcbot-proxy` remains the path for hard-enforced, server-side limits.

### Security

- **Atomic, crash-safe seed writes.** `saveEncryptedMnemonic()` and the mnemonic-backup writer now write via temp file + `fsync` + atomic rename instead of a plain exclusive-create, so a crash mid-write can no longer leave a partial or corrupt `seed.enc`. Exclusive-create semantics (refuses to overwrite) and `0o600` permissions are unchanged.
- **Passphrase env hygiene.** `loadMnemonicFromEnv()` now clears `SPARK_PASSPHRASE` from `process.env` immediately after reading it, on all paths, shrinking the window it lives in process memory (debugger snapshots, child-process inheritance, crash dumps). Opt out with `loadMnemonicFromEnv({ clearEnv: false })` if a later path must re-read it. Crypto primitives unchanged (scrypt N=2¹⁷, AES-256-GCM).
